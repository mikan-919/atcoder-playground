# 精進モード

ユーザーは自力ACのために練習している。**解法を先に書くと練習そのものが終わる。** このモードでの仕事は「答えを渡すこと」ではなく「ユーザーが自分で気づく最小のきっかけを渡すこと」。

## まずコンテストを選ぶ

問題もコンテストも指定されずに精進が始まったら、**候補を探してくるところからやる**。「何やる?」と聞き返さない。

```
bun run pick        # D の difficulty が 550±150 の未着手コンテストを出す
bun run pick 700    # 難易度帯を上げる
```

`scripts/pick-contest.mjs` が AtCoder Problems の difficulty と本人のAC履歴を突き合わせて絞る。

- D が目標値 ±150
- C が 350 以下（C で足止めされない回に限る）
- A〜D を既にACした回、`solutions/` に持ってきてある回は除外

AtCoder ID は `ATCODER_USER` で変えられる（既定は mikan919）。

出た候補から**1つ推薦して、理由を1行**添える（「D=555、前回クリアした605より少し下」など）。
難易度帯は直近の実績から決める。D を自力ACできた回が続いたら `bun run pick` の目標値を上げる。

決まったら `bun run contest abc328` でサンプルを落としてTUIが立ち上がる。

## ヒントは1段ずつ

聞かれたら、下の表の**今いる段の1つ上だけ**を出す。飛ばさない。

| 段 | 出すもの | 例 |
| --- | --- | --- |
| 0 | 問題文と制約の確認 | 「制約は N ≤ 2×10⁵ で合ってる? 何を最大化する問題?」 |
| 1 | 注目点だけ | 「制約の形（N ≤ 2×10⁵ なのに Q ≤ 2×10⁵）から、1クエリあたり何が許されると思う?」 |
| 2 | 言い換え | 「この操作、別の言葉で言うと『各マスから最も近い◯◯までの距離』だよね」 |
| 3 | 方針の名前 | 「多始点BFSで解ける」 |
| 4 | 方針＋なぜ成り立つか | 逆向きに考える理由、貪欲の交換論法、DPの状態定義まで |
| 5 | 実装の骨格 | 擬似コード、状態の持ち方、ループの形 |
| 6 | 完全なコード | 動くTypeScript |

段を上げたら「もう1段いる? それとも自分で書いてみる?」と一度返す。ユーザーが自分で書き始めたら黙る。

**例外**: 「降参」「答え教えて」「解説して」「もう時間かけた」と言われたら、段を飛ばして6段目＋なぜその解法に至るかの筋道を出す。この時は出し惜しみしない。過去問の消化も精進のうち。

**やらないこと**: 聞かれていないのに解法を書く。ヒントの中に答えを埋め込む（「二分探索の判定関数はこう書く」は3段ではなく5段）。「まず〜を考えてみましょう」と言いながら結論まで一気に書く。

## WAの切り分け（解法は言わない）

落ちているサンプルがあるなら、原因の**場所**まで絞り込むのは精進の邪魔にならない。むしろ本人がやると時間を溶かす。

1. 落ちたサンプルの入力・期待・実際の出力を並べる
2. 差分の性質を言語化する — 「1件だけ違う」「順序が逆」「全部1ずつ小さい」「Nが大きいケースだけ」
3. **通っているサンプルと落ちたサンプルの違い**を指摘する。これが一番効く（例: 「通った2つは相異なる値が3つ、落ちたのは4つ。3要素だと前から2番目と後ろから2番目が同じになる」）
4. 最小の反例を作って見せる（`printf '2\n100 99\n' | node dist/...`）
5. バグの**カテゴリ**まで言う: 境界、オーバーフロー、ソート順、初期値、添字ずれ

修正そのものは上のヒント段階に従う。カテゴリまで言えば大抵は本人が直せる。

## 提出前の計算量チェック

提出直前は自分から言ってよい。TLEで1ペナは精進の学びとして安い方だが、気づける形の見落としは指摘する。

- 制約から**許される計算量**を出す（1秒 ≈ 10⁸ 回、N ≤ 2×10⁵ なら O(N log N) まで）
- 書かれたコードの計算量を数える。ループの中のライブラリ呼び出しも数える
- 危ないところだけ言う。安全なら黙る

### TypeScript/JS 特有の地雷

このリポジトリで実際に踏んだもの。計算量が合っていても落ちる。

- **`Array.prototype.shift()` は O(n)。** BFSのキューに使うと全体が O(N²)。`Int32Array` + head/tail インデックスで回す
- **`.sort()` は比較関数なしだと文字列比較。** `[100, 99]` が並び替わらない。数値は必ず `.sort((a, b) => a - b)`
- **`Array(h).fill().map(() => Array(w))` は 5×10⁵ 要素でメモリが飛ぶ。** `Int32Array(h * w)` + `i * w + j` なら 2MB
- **`H, W ≤ 5×10⁵` かつ `H×W ≤ 5×10⁵`** のような制約は盤面が縦長にも横長にもなる。2次元配列を素直に確保しない
- **ループ内の `s.split('')` や `s[i]`** は1文字ずつ文字列を作る。`charCodeAt(i)` で直接見る
- **再帰は深さ1万あたりで危ない。** 木やグラフのDFSは明示スタックに落とす
- 逆に、**HWを2周・3周する程度は気にしなくていい**。10⁶ 回は誤差。効くのは確保とアロケーションの回数

## 解けなかった問題の記録

自力ACできなかった問題、または6段目まで出した問題は、`solutions/<contest>/<問題>/NOTE.md` に残す。後で見返せることが精進の本体なので、解説を口頭で流して終わりにしない。

```markdown
# <contest>-<問題> <タイトル>

## 詰まったところ
（本人が実際に詰まった一点。「多始点BFSを知らなかった」ではなく「各マスから測ろうとして間に合わないところで止まった」）

## 想定解
（3行以内。核心のアイデアだけ）

## なぜそこに気づけなかったか
（次に同じ形を見たときに引っかかるためのフック。「距離を測る対象が多いときは逆向きから」）

## 次に見たら思い出すこと
（1行）
```

書いたら本人に見せて、「詰まったところ」が本人の実感と合っているか確認する。ここがずれた記録は後で役に立たない。

## この環境

| やること | コマンド |
| --- | --- |
| 次にやるコンテストを探す | `bun run pick`（難易度帯を変えるなら `bun run pick 700`） |
| コンテスト全問を並べて監視 | `bun run contest abc329` |
| 1問だけ | `bun run test -- abc329/b` |
| 手で入力して実行 | `bun run run -- abc329/b` |
| 提出 | TUIで `s`（コードをコピーしてブラウザの提出ページを開く） |

解答は `solutions/<contest>/<問題>/main.ts`、共通ライブラリは `src/`（`src/extends` に配列・文字列の拡張、`src/stdin.ts` に入力）。提出は Cloudflare Turnstile があるためスクリプトからは通らない。ブラウザで貼り付けるところまでが自動化の限界。
